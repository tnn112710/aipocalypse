# Enemy AI in aipocalypse

Project layer on top of the library skills. Read those for the API: **unity-behavior-designer-pro** (BD Pro 3.3.3: tasks, trees, aborts, events, Manual mode) and **unity-astar** (A\* 5.4.7: FollowerEntity, graphs, queries, pooling). Where they and this file disagree, this file and `docs/technicals/` win.

What exists, file by file, is already documented. Read it, don't re-derive it:
- `docs/technicals/ARCHITECTURE.md` → **AI** (the wander slice, how a scene gets enemies, the tick budget, the Navigation prefab), **Entities** (crowd vs unique entities, `IPlayerTarget` / `PlayerRegistry`), **Performance** (allocation and central-tick rules), **Prototypes → main game**.
- `docs/technicals/CODE_STRUCTURE.md` → `_Core/EnemySystem/` rows, `Content/Enemies/`, the scope/installer and frame-order diagrams.
- `docs/technicals/PLUGINS.md` → A\* and Behavior Designer Pro rows, the plugin rules (per-instance plugin components on crowd entities: only `BehaviorTree` and `FollowerEntity`), the wander-demo / navmesh note.
- `docs/technicals/ENVIRONMENT.md` → **Navigation** (WorldMap's graph, water volume, `Navigation.Bake`, when to re-bake).
- `docs/ROADMAP.md` → `Proto_Enemies` (next enemy work and its gate).

The rest of this file is what those docs don't spell out: the contracts the code relies on, and the rules for extending it. References:
- [references/behaviour-catalogue.md](references/behaviour-catalogue.md): what the GDD asks of each agent family (raiders, bosses, animals, companions, robots), with source (canon / idea / open) and the blocks it needs.
- [references/enemy-design.md](references/enemy-design.md): designing what each agent asks of the player: the readable-and-fair rules every agent meets (telegraphs, damage matching looks, off-screen softening, fair senses, visible state, a way to give up), the roster (one job per kind, archetypes at the extremes, scarce ammo), hits and feedback in first person, survival threats (thieves, breakers, the end of a raid, pursuit limits, night and light, tone, livestock), bosses, giants and elite minibosses.
- [references/encounters-and-waves.md](references/encounters-and-waves.md): combining them: a spec sheet per kind and behaviour types (Level Up!), composing fights, a raid night's warnings and pacing (intensity cycle, wave slots), spawning and formations, introducing new kinds, difficulty over days (levers, credit budgets, formulas from shipped games) and a proposed raid data shape.
- [references/building-blocks.md](references/building-blocks.md): eight building blocks from shipped games (engagement slots, raid director, perception, think-rate LOD, companion follow, boss maneuvers, routines and needs, squads), ranked, mapped to our services and trees. None is built.
- [references/tree-specs.md](references/tree-specs.md): trees as text and [scripts/TreeKit.cs](scripts/TreeKit.cs) (`Tasks`, `Check`, `Build`, `Describe`).

## 0. Designing a behaviour (any agent: enemy, animal, companion, NPC)

1. **What and why.** Find the behaviour in the catalogue and say where it comes from. Anything from the GDD is proposed and confirmed first (AGENTS.md → Prompt first, GDD second); the user's prompt is the spec.
2. **Where it lives.** Cross-agent decisions (who attacks, when to spawn, what to steal, retreat at midnight) go in a service ([building-blocks.md](references/building-blocks.md) → Rules); the tree only picks this agent's next action. Prefer new data over a new tree, a new tree over a new task.
3. **Answer the player-facing questions** before drawing branches: its job (the one player habit it punishes); what it does unaware; how it notices the player or its target (sight, sound, told by a service); what it does then; how it warns before each attack; when it gives up, retreats or changes tactics; for a boss, which player skills it tests and how the fight changes. Agents that don't fight (animals, robots) answer the same about their own triggers. A blank answer is a question for the user, not a default to invent. The answers head the spec as `#` comments; the rules they must meet are in [enemy-design.md](references/enemy-design.md) §1, with roster, survival-threat and boss guidance in its later sections. A wave, a raid night, a new kind's debut or a difficulty change is designed as data first, with [encounters-and-waves.md](references/encounters-and-waves.md).
4. **Write the tree as a spec** ([tree-specs.md](references/tree-specs.md)) and show it to the user before building. `TreeKit.Tasks` lists the blocks that exist (ours under `Aipocalypse/…`, BD built-ins, the Movement Pack); reuse shared subtrees (`SubtreeReference`) rather than copying branches. `TreeKit.Describe` prints any existing tree for comparison.
5. **Write the missing tasks** (§3), small and backed by tested components. With Atlas connected, check them against the installed API (`review-opsive-code`).
6. **`Check`, `Build`, read back**: Build returns the asset described back. Assign the subtree on the prefab through its setup script (`m_Subtree`, §1), never by hand-editing YAML.
7. **Verify in play**: enter play, probe the agent with `script run` (`EnemyBrain`, `tree.Status`, `GetRuntimeNodeStatus`) or the Behavior Designer window, then stop. Also check it from the player's seat: every attack is preceded by its warning and every state change can be seen or heard. When it misbehaves: `Describe` the asset, and with Atlas connected `diagnose-opsive-problem` on the selected agent.

## 1. Enemy prefab contract

Checked against `Content/Enemies/WanderCapsule/WanderCapsule.prefab` and `_Core/EnemySystem/`:

- `BehaviorTree`: **Update Mode `Manual`**, **Start When Enabled off**, **Pause When Disabled off**, Evaluation Type `EntireTree`, and the kind's subtree assigned on the component (the capsule uses `Content/Enemies/_Shared/Wander.asset`, the goblins `Melee.asset`). Nothing assigns `Subgraph` at runtime; setup scripts set the serialized `m_Subtree` (`BuildGoblin.Upgrade`).
- `FollowerEntity` (radius 0.5, height 2 — the WorldMap graph is baked for this shape), local avoidance on, gravity on, `groundMask` = Default only.
- `EnemyMover` and `EnemyBrain` (`[RequireComponent]` enforces `BehaviorTree` + `EnemyMover`; `EnemyMover` requires `FollowerEntity`). `EnemyBrain._definition` set to the kind's `EnemyDefinition` (base stats for every `EnemyStat` — `MaxHealth`, `MoveSpeed`, `AttackDamage` —, `Reaction`, `Wander`, `Melee` and `Targets` when its tree fights, `Sounds` for its voice and steps), or it logs an error and never starts.
- A `Spawnable` on the prefab root (SpawnSystem: pool, life, alive or retired; `EnemyBrain` requires it, but an old prefab only gets it on disk when it's added and saved: `AgentScripts/Spawning/SpawnSystemSetup.cs`). Spawned kinds have an `EnemySpawnCard` next to them (`Content/Enemies/<Name>/<Name>_Card.asset`: a `SpawnCard` with prefab variants by weight as `Spawnable`s, group size, placement on the navmesh, plus the arrival cue), listed in `EnemySystemSettings.Cards` (`EnemySpawningTests` checks).
- `EnemyBody` with `_visual` (the child that sinks after death) and at least one non-trigger collider on the `Enemy` layer: that is what bullets and swings hit (`DamageService.DealHit` finds the `IDamageable` in the collider's parents). `EnemyCombatTests` checks both.
- Weak spots: a `Hitbox` (`_Common/Combat`) on a collider scales hits there and can make them critical. Animated kinds put a ×2 critical sphere on the head bone. No other collider may wrap it: the goblins' root capsule ends at the hips and a sphere on the upper chest covers the torso, all riding the bones so they follow the pose (`BuildGoblin.AddHeadHitbox`). Check with `ProbeCombat.HeadRays`; `EnemyCombatTests` checks the bind pose.
- Layer **`Enemy`**, which keeps the enemies out of the recast scan and out of grounding queries.
- No `EntityScope`, no `Seeker`/`RVOController`, no other per-instance plugin components, no `Update()`.
- Animated kinds (the Goblins) add `EnemyAnimator` and a nested `Model` child with the Animator, and their definition links `Animation` settings. Everything about the model and animation is in **aipocalypse-characters**.

## 2. Lifecycle and ticking (what tasks can rely on)

- **Injection first, then the tree.** `EnemyBrain.Construct` gets `EnemyRegistry` and the scene's `AstarPath`. Activation (`EnemyMover.Initialize` → `Tree.StartBehavior()` → `EnemyRegistry.Add`) waits for both injection and the brain's first `Start`, whichever comes last. So a task's `OnAwake`/`OnStart` always sees an initialized mover.
- **Stats per life.** Each activation builds a fresh `EnemyStats` from the definition (`EnemyBrain.Stats`). Read tunable numbers through it, never from the definition at runtime, and apply a temporary change as a modifier with a source (`AddModifier` / `RemoveModifiers(source)`); the brain re-applies `MoveSpeed` and `MaxHealth` on `Changed`. A new stat: append to `EnemyStat`, give every definition a base value, and apply it in `EnemyBrain.ApplyStat` (or where it's read). Each life also gets a random `MoveSpeed` modifier (1 ± `EnemyDefinition.SpeedVariance`, source the brain).
- **Staggered.** A heavy enough hit (`StaggerMeter`, its kind's `StaggerProfile`) calls `EnemyBrain.Stagger`: the mover halts and the tree doesn't think for `StaggerTime`, then carries on where it was. A task that walks or swings must notice: compare `EnemyBrain.Interruptions` with the count it started with and start over when it changed (`ChaseTarget` sets off again, `MeleeAttack` cancels the swing so no blow lands late). A flinch is only a `MoveSpeed` modifier and needs nothing from tasks.
- **Appearing.** An enemy brought in by `SpawnService` appears first (`EnemyBrain` is the prefab's `ISpawnable`: `OnSpawned` teleports its agent and calls `Appear`): its appear clip plays and `EnemyBrain.Think` skips the tree for `AppearTime` + jitter, so tasks first run after that. Placed enemies don't appear.
- **Death.** `EnemyBody` at 0 HP: colliders off, `EnemyBrain.Die()` (leaves the registry, stops the tree and the mover, like a disable), death animation, then after `EnemyReactionSettings.CorpseTime` the visual sinks and the body disables the GameObject. Tasks never see a dead enemy (it's no longer ticked); systems that hold enemies check `EnemyBrain.IsDead`.
- **Enable/disable is the spawn/despawn switch.** `OnDisable` leaves the registry, frees its attack slot, `StopBehavior(false)` and halts the mover; the root's `Spawnable` hands a spawned enemy back to its `PrefabPool`. `OnEnable` (after the first start) activates again. Re-activation re-runs `EnemyMover.Initialize`, which re-reads speed (the new `EnemyStats`) and stop distance and sets `Home = transform.position`. So `PrefabPool.Get` positions the enemy **before** `SetActive(true)`, and `OnSpawned` calls `EnemyMover.Teleport` after enabling (unity-astar → Pooling). `Die()` also retires the `Spawnable` (no longer counted as alive by handles and caps). Prewarming wakes each instance once off-stage (`SpawnState.Warming`: it sets up, paying `Awake` and `Start` while loading, but doesn't register or think), then parks it under an inactive root until taken.
- **Only `EnemyManager` ticks enemy trees.** Don't add an `Update`, a coroutine or a second ticker. Budget: `Data/Enemies/EnemySystemSettings.asset` (`ThinkInterval` 1/15 s, `MaxThinksPerFrame` 200 visits; enemies past `FarThinkDistance` 60 m from the player think only every `FarThinkInterval` 0.25 s). Consequences for tasks:
  - A `Running` task is re-entered about 15 times a second, not every frame, and less often past the per-frame cap. Check state (`Arrived`, `TimedOut`) and timestamps (`Time.time >= _until`); never accumulate per tick.
  - Scaled time: while `TimeService` pauses the game, trees don't think and `FollowerEntity` freezes too. Use `Time.time`/`Time.deltaTime`; never the built-in time-scale tasks.
  - A tree that disables its own enemy mid-tick is safe (swap-remove; the swapped-in enemy waits a turn).
  - `EnemyManager.Advance(deltaTime)` exists for tests; the profiler marker is `Aipocalypse.EnemyManager.Think`.

## 3. Writing tasks and subtrees here

Follow `_Core/EnemySystem/WanderTasks.cs`:
- Tasks are `ActionNode` / `ConditionalNode` in the namespace of the system that owns them (`Aipocalypse.Core.EnemySystem` today), with `[Category("Aipocalypse/<Subtree>")]`. A stackable `Action`/`Conditional` (the Movement Pack's tasks, many built-ins) only sits in a graph inside a `StackedAction`/`StackedConditional` node; TreeKit wraps it for you. Project code style applies (AGENTS.md → Code style), not Opsive's `m_` style.
- Cache `EnemyBrain` and `EnemyMover` in `OnAwake`. Tuning comes from `_brain.Definition` (and the settings asset it links, e.g. `Definition.Wander`), never literals in the task or the graph.
- Hand-offs between tasks go through brain properties (`EnemyBrain.Destination`), not blackboard variables; the trees have no shared variables today. Add a variable only when designers need to bind it.
- Movement only through `EnemyMover`; add a method there rather than touching `FollowerEntity` from a task. Undo in `OnEnd` (`Halt()`), which also runs on aborts.
- Navmesh queries go through `EnemyMover` (an enemy's own: `TryFindDestination`) or `EnemyNavigation` (anyone's: `TrySnap`, `IsReachable`), both on the injected `AstarPath` (`GetNearest` + `PathUtilities.IsPathPossible`). Never `AstarPath.active`.
- Subtree assets live in `Content/Enemies/_Shared/` when shared, else in the agent's folder. **Generated trees** have a spec in `AgentScripts/Enemies/<Name>.tree.txt` (`Melee`) built by `TreeKit.Build`, which keeps the asset's GUID; edit the spec, never the generated tree in the window (a rebuild overwrites it). `Wander.asset` is hand-drawn: edit it in the window, or move it to a spec first (`Describe` writes one). The serialized task data is binary-encoded, so never hand-edit `.asset` YAML.
- **Conditional aborts here:** a conditional re-checked by an abort runs `OnUpdate` again, so it may set brain state (`ChooseTarget` sets `Target`). An abort fires only when the conditional's result *changes*: a branch that fails while its conditional still succeeds falls to the next branch and stays there (the conditional didn't change). So fight tasks return Success to restart the hunt (`MeleeAttack` when the target steps back or its slot is gone), and Failure only when the target is gone.
- Trees store each task by its full type name (`Aipocalypse.Core.EnemySystem.ChooseWanderDestination` in `Wander.asset`). Renaming a task class or moving its namespace breaks every tree that uses it: rename only with the user, then fix the name in the specs and rebuild (hand-drawn trees: re-open and fix them in the Behavior Designer window).
- **Atlas** (Opsive's assistant, PLUGINS.md → AI & navigation): when its `atlas` MCP tools are connected, use them through its `build-opsive-behavior`, `diagnose-opsive-problem` and `review-opsive-code` skills to check the installed BD Pro API (`atlas_get_api_contract`, `atlas_search_knowledge`), validate tasks (`atlas_validate_artifacts`), stage and apply them and read compiler diagnostics, and to snapshot selected trees when diagnosing. Write the task code yourself: `atlas_generate` is denied in user settings because it bills through Atlas's provider. Atlas doesn't build or wire trees (TreeKit does), and its skills don't know this file: the rules here and AGENTS.md → Code style win over its suggestions (GameObject tasks only, no ECS; no `m_` fields; movement through `EnemyMover`).

**New enemy kind:** `Content/Enemies/<Name>/` with the prefab (variant of an existing one where possible) and its `EnemyDefinition` asset; reuse a subtree, or add one plus its settings ScriptableObject (`Data/Enemies/` or shared) referenced from `EnemyDefinition`. Prefer new data over a new tree, a new tree over a new task. What the GDD asks of every agent family (raiders, bosses, animals, companions, robots) is collected in [references/behaviour-catalogue.md](references/behaviour-catalogue.md); the archetypes (rusher, tank, ranged, flyer, swarm, sneaker) and the thief / breaker / hunter jobs are IDEAS.md drafts. Behaviour and numbers taken from any of it must be proposed and confirmed before building (AGENTS.md → Prompt first, GDD second). Update CODE_STRUCTURE.md and ARCHITECTURE.md → AI in the same change.

**Movement Pack** (PLUGINS.md, tag Could): Opsive's Seek / Flee / Pursue / Evade / Follow / Patrol / cover tasks. They move through a `Pathfinder` chosen per task in the inspector; only an A\* adapter may be picked here, never the shipped `NavMeshAgentPathfinder`. The adapter (`EnemyMoverPathfinder : Pathfinder`, not built yet) forwards `SetDestination`, `HasArrived`, `Stop`, `Speed`, `Velocity` and `SamplePosition` to `EnemyMover`, so A\* queries still use the injected `AstarPath`. Its tasks read the target from a `SharedVariable<GameObject>` that the brain sets (`SetVariableValue`), the one place trees take a shared variable. Use a pack task where it beats a small one of ours (pursuit prediction, evade, cover search); keep our `Wander` subtree and project-specific tasks. In a spec: `Flee Pathfinder=new:EnemyMoverPathfinder Target={Target} FleedDistance=15`. Opsive's own A\* integration (a separate download) targets AIPath-style agents and doesn't mention `FollowerEntity`; ours goes through `EnemyMover` so speed, stats and halts stay in one place.

**Senses Pack** (PLUGINS.md, tag Could, not used yet): Opsive's perception conditionals (`CanDetectObject`, `WithinRange`, `GetSensorAmount`…) over a `Sensor` chosen per task (`Visibility`, `Sound`, `Distance`, `Luminance`, …). Candidate for line of sight once it's asked for. Each sensor runs physics queries when its task ticks, so it stays inside the time-sliced think, and its result goes to the brain rather than replacing `TargetSelector`. `Sound` reads `AudioSource`s under the target and so can't hear BroAudio; hearing needs our own noise events. Its emitter managers are self-creating singletons: none on crowd entities.

## 4. Wiring in this codebase

- **VContainer** (unity-vcontainer): `EnemyInstaller` is the only registration point (a `SceneInstaller` on the scene's `GameLifetimeScope`). Enemies are crowd entities: injected once, no scope of their own. Services reach tasks only through `EnemyBrain`: add the dependency to `EnemyBrain.Construct` (setup time), expose what tasks need. BD tasks are never injected.
- **Spawning:** code spawns only through `SpawnService` (SpawnSystem, [SPAWNING.md](../../../docs/technicals/SPAWNING.md)): `Spawn(card, position, rotation)` now, or `Spawn(SpawnRequest.Group(card, zone, count) / .At(card, point, count) / .Of(squad, zone) / .From(table, conditions, zone))`, with `.With(formation)`, `.WithRules(rules)` and `.Facing(direction)`. It returns a `SpawnHandle` (`Count`, `Pending` counted as alive, `Alive`, `Spent`, `Cancel`, `Despawn(Now | WhenUnseen)`). Members are picked from the card, taken from the `PrefabPool` (made with the scene resolver, so injected before `Awake`) and woken within `SpawnSystemSettings.SpawnBudgetMs` (2 ms) a frame; a prewarmed goblin costs about 1.1 ms. A plain `Instantiate` gives an un-injected enemy that logs an error and never thinks. Raids (RaidSystem, [RAIDS.md](../../../docs/technicals/RAIDS.md)) and `enemy.spawn` go through it; EnemySystem never knows about raids, and SpawnSystem knows nothing of enemies (it places walkers through `INavmeshQuery`, which `EnemyNavigation` implements). Open-world camps or herds are `SpawnArea`s run by `PopulationDirector` (WorldMap: `Spawn Areas/Goblin Camp (Lake)`, 4 goblins). Pools are reserved per owner (`Prewarm(card, count, owner)` / `Release(owner)`; raids and areas do it) and trimmed past the reservations. Enemies placed in a scene are still collected by `EnemyInstaller` on save / entering Play (none are placed in WorldMap today).
- **A\***: the installer registers the `AstarPath` from the scene's `Navigation` prefab instance; `EnemyBrain` passes it to `EnemyMover.Initialize`. PLUGINS.md's A\* row mentions an `INavigation` service; it doesn't exist yet. Until it does, keep A\* queries inside `EnemyMover` or `EnemyNavigation` using the injected instance.
- **MessagePipe** (unity-messagepipe): no enemy events exist yet (a kill is `DamageDealt` with `Result.Killed`); shared event structs live in `_Core/_Common/Events/` (`DamageDealt`, `PlayerDied`, `DayPhaseChanged`…). When enemies need them: one subscriber in the enemy system routes to the affected `EnemyBrain`, which forwards to its tree (`EventHandler.ExecuteEvent` / `SetVariableValue`); no per-enemy subscriptions. Outbound: tasks call the brain or a service, which publishes.
- **Grass bending:** `EnemyBrain` `TryResolve`s the scene's `GrassBendField` (EnvironmentSystem, registered by `EnvironmentInstaller`) and joins it while active with `EnemyDefinition.GrassBendRadius`. Animals and other crowd movers do the same (`Add(transform, radius)` / `Remove`); never a Stylized Grass `GrassBender` per crowd entity.
- **Targeting:** enemies hunt `ITargetable`s (`_Common/Entities`: `Transform`, `TargetKind`, `IsTargetable`). `TargetRegistry` holds the active player (from `PlayerRegistry.Current`) plus whatever registers itself (fence segments and gates as `IBreachable`, kept apart; crops, animals later); `TargetSelector.Choose` scores kind weight (`EnemyDefinition.Targets`) per metre, skipping untargetable ones (dead, `cheat.notarget`). With no path to that target (`INavmeshQuery.IsReachable`) and a Fence weight in `Targets`, it attacks the weakest of the `MeleeSettings.BreachCandidates` (5) nearest standing barriers instead; tasks aim at `ITargetable.PointFor(from)` (a barrier's face on the attacker's side) ([DEFENSE.md](../../../docs/technicals/DEFENSE.md)). `EnemyBrain.ChooseTarget` re-asks it every `MeleeSettings.RetargetInterval` and sets `EnemyBrain.Target` (cleared on death and disable). `Engaged` (inside `EngageRadius`, set by `ChaseTarget`) drives the fighting stance and the shout. `AttackSlots` caps how many enemies close in on one target (`EnemySystemSettings.AttackersPerTarget`: player 3, fence segment 3); the rest wait at `HoldDistance`. A blow is `EnemyBrain.Strike` → `DamageService.Deal` (`AttackDamage` stat) when `MeleeHit.Lands` at `HitTime`.
- **Sounds:** `EnemyVoice` (one per brain) plays the kind's `EnemySoundSet` through `AudioService.PlayAt` from the existing hooks (`MeleeAttack` swing and impact, `EnemyBody` hurt and death, `Engaged` shout), rate-limited. Footsteps come from `EnemySoundManager`'s central tick (per stride, within `FootstepRange` of the player, capped per second): never an `AudioSource` or `Update` per enemy.

## 5. Scenes and navigation

- Every scene with agents needs `_Core/EnemySystem/Prefabs/Navigation.prefab` (AstarPath + RVOSimulator) and an `EnemyInstaller` on its `GameLifetimeScope` with that `AstarPath` and the settings asset assigned (the installer reports a `Problem` otherwise).
- The prefab's default graph (small terrain-following grid, scanned on startup) is for small prototype scenes. WorldMap's instance holds the cached recast graph produced by the map generator: re-bake with the generator's `Navigation` steps after collider, terrain or water changes, never a hand scan without the water mesh (ENVIRONMENT.md → Navigation). Changing the enemy `FollowerEntity` radius/height means re-baking at the new size, or a second graph per size.
- Scenes today: only `Scenes/Prototypes/WorldMap.unity`. No enemy is placed in it: raids spawn goblins from `Raid/Spawn Zone (Front)` at the gate every night at 20:00 (RAIDS.md), and `enemy.spawn goblin [n]` spawns some by hand. `WanderCapsule.prefab` remains as the bare contract. `Proto_Enemies` / `Proto_Stress` are planned (ROADMAP), not created. `Tests/PlayMode/WorldMapSmokeTests` jumps the clock to the raid's start hour and asserts raiders spawned.

## 6. Performance

- No per-system enemy budget is written in ARCHITECTURE.md yet. The ROADMAP gate stands: 300 tree-driven enemies within budget before adding more archetypes (`enemy.spawn goblin 300` sets it up; raids cap at `RaidSettings.AliveCap`, 12); record the measured budget in ARCHITECTURE.md → Performance when it exists. `AgentScripts/Raids/RaidSoak.cs` plays a whole raid night with `cheat.autopilot` and reports frame times.
- First levers are the settings asset (`ThinkInterval`, `MaxThinksPerFrame`); then the escalation order in unity-behavior-designer-pro §5. Entity (ECS) tasks or baking agents to subscenes break "no ECS in our code" and need the user's sign-off.
- Profile with the Behavior Designer window closed and A\* gizmos off; watch `Aipocalypse.EnemyManager.Think`, `AIMovementSystemGroup`, `RVOSystem`.
- Known deviation: `WanderCapsule.prefab`'s `FollowerEntity.debugFlags` is `Path` (64); set it to none on enemies built from it (the Goblin prefabs have it off).

## 7. Not built yet (don't assume these exist)

Line of sight and hearing (raiders always know their target; `ChooseTarget` is distance and weight only; the Senses Pack is installed but unused), enemy damage resistances, the `EntityRegistry` spatial grid (ROADMAP → Foundation), enemy events, distance LOD, the `INavigation` service, the Movement Pack adapter. Target kinds other than the player and fences (crops, animals, drops, exits), quiet nights, the difficulty ladder, Blood Moon and eclipse, ranged enemies (spear throwers), the midnight retreat, flying movers, animals, companions (drone, dog, cat), service robots and bosses exist only in the GDD ([references/behaviour-catalogue.md](references/behaviour-catalogue.md)): any behaviour taken from it is proposed and confirmed first, and the building blocks for them are in [references/building-blocks.md](references/building-blocks.md). When they land, unique agents follow unity-behavior-designer-pro §1 (own `EntityScope`, `EveryFrame` or Manual from their own system), and their notes belong in ARCHITECTURE.md → AI and here.
