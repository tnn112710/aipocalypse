# Architecture

DI with **VContainer** (no gameplay singletons), events with **MessagePipe**, async with **UniTask**, input through one **InputService**, camera through **Cinemachine**.

The design is still moving, so the architecture is built to absorb change: a small stable **Core**, swappable **Features** on top, everything tunable in data, and events as the joints between them.

This file describes what exists. Each section keeps its rules for the systems still to come; when a system lands, fill in its part of the section. Script-by-script map: [CODE_STRUCTURE.md](CODE_STRUCTURE.md).

## Core vs Features

| Core — build now, rarely changes | Features — *provisional*, built when the design settles |
| --- | --- |
| Movement, look, stamina, fall damage, `Health` | *None yet* |
| Stat reads (`IStatProvider`) | |

- **Features → Core only.** Core never references a feature. Enforced by assemblies (see Assemblies).
- **One feature = one folder + one installer.** Cutting a feature = removing its installer; Core still compiles and runs.
- Core exposes **seams** with plain defaults; features plug better implementations in. Today: the player reads speeds, costs and max meters through `IStatProvider` (default `BaseStats` returns the tuning value); a perks/XP feature will replace it.
- A GDD change should only touch Features. If it forces a Core change, that's a signal to add a seam.

## Layers

```text
VIEWS     MonoBehaviours (Player). Physics, camera, input -> intents. [SerializeField] for prefab parts, [Inject] for services.
RULES     Plain C# that owns the rules (PlayerMotor, Stamina, Health, InputService). Services registered in VContainer
          publish gameplay events and never reference MonoBehaviours directly — use an interface.
STATE     Plain [Serializable] classes, no Unity refs (meters today: Health, Stamina).
DATA      ScriptableObjects: defs, tuning, tables (PlayerTuning and its groups). Read-only at runtime.
```

Dependencies point down only.

## Gameplay events

Core **announces** what happens; features **react**. New rules are new subscribers, not edits to existing code.

- Events are small `readonly struct`s published through MessagePipe (`IPublisher<T>` / `ISubscriber<T>`, injected). Brokers are registered once in the root scope.
- Core events live in `_Core/_Common/Events`: `DamageDealt`, `PlayerDied`, `PlayerDeathSequenceEnded`, `PlayerRespawnFading` and `PlayerRespawning` (async), `RespawnStageChanged`, `PlayerRevived`, QTE lifecycle (`QteStarted`, `QteAttempted`, `QteEnded`), gun jam / repair beats, world time (`HourChanged`, `DayPhaseChanged`, `DayStarted`, `TimeJumped`, `TimeSkipEnded`), raids (`RaidStarted`, `RaidWaveStarted`, `RaidEnded`), fences (`BarrierBroken`, `BarrierRestored`). Features may define their own.
- **Damage goes through `DamageService.Deal`** (root scope): it applies `IDamageable.TakeDamage` (which returns a `DamageResult`: applied amount, killed) and publishes `DamageDealt` with the hit's `Source`. Physics hits (bullets, swings) use `DamageService.DealHit(hit, info)`, which finds the collider's `IDamageable`, deals the damage and pushes a loose rigidbody by `info.Force`. Weapons, falls and future traps never call `TakeDamage` directly, so hit feedback, kill credit and damage rules hook in at one place.
- **Sound goes through `AudioService`** (root scope), a thin wrapper over BroAudio: game code plays `SoundID`s and never calls BroAudio's static facade.
- Events are for things that *happen* (a hit, a death), never per-frame data (positions, timers).
- Inside one system, plain C# events are fine (`PlayerMotor.Landed`). Across systems, use MessagePipe.

## Composition and data

**Entities are built from parts, not class hierarchies.** The player is `PlayerLife` + `PlayerMotor` + `PlayerLook` + `PlayerCameraRig` + `Stamina` + `PlayerHeadBob` + `HeldItemDriver` and a few more, plain C# parts driven by one view (`Player`). Future entities follow the same pattern.

**Every number lives in data.**

- Settings shared by a whole system (one copy each) are ScriptableObjects under `Assets/_Game/Data/<System>/` (today: `Player/PlayerTuning.asset`, which links one asset per group: movement, vitals, camera, interaction, held item, sounds, vision). Data that belongs to one thing (a gun's `GunDefinition`, an item, an enemy's stats) lives with that thing in `Assets/_Game/Content/<Kind>/<Name>/` (see Folder layout). SO edits made in Play mode persist, so tune by feel while playing.
- Rules that are really tables are data tables, not `if` chains.

## Scopes and app flow

```text
Root (VContainerSettings → ProjectLifetimeScope prefab, auto-created before any scene)
  InputService · MessagePipe brokers · SaveService · SaveRegistry · GameSession · SceneLoader (+ loading screen) · … (SettingsService later)

MainMenu scene (first in Build Settings, no Boot scene)
  HudScope on the menu canvas (root services): MainMenuScreen: Continue | Prototype | Load Game | Settings (later) | Quit

World scene (one persistent map, no mission/night scopes)
  GameLifetimeScope: installers for Core + enabled Features; WorldSaveInstaller → WorldSaver: on the first frame GameSession
  restores the pending save (or starts a new game), then autosaves each morning. Details: SAVE.md
  Pause menu → Main Menu → load MainMenu (scene unload disposes all game services)

Any scene (World, Proto_*, test arenas)
  Entity prefabs carry their own EntityScope — see Entities
```

- **Play from any scene:** the root scope always exists. Play pressed in a world scene (no menu), like Prototype in the main menu, starts a fresh game on day 1 that saves to the editor-only "Editor Save" slot. A `DevStartConfig` (start day/time, inventory, which features are on) is still a later idea.
- Scenes load only through the root `SceneLoader` (`SceneManager.LoadSceneAsync` + UniTask, under a loading screen). Addressables hold only Localization's string tables ([LOCALIZATION.md](LOCALIZATION.md)); no scene or content is loaded through them.
- **Built so far:** the root (`VContainerSettings` + `ProjectLifetimeScope` prefab) with MessagePipe, `LanguageService` (`LocalizationInstaller`), `InputService`, `AudioService`, `DamageService`, `TimeService`, `GraphicsService`, `QuickTimeService`, `PlayerRegistry`, `PlayerRespawnFlow`, `EffectPool` (`EffectsInstaller`), `BulletSystem` and `GunJamFactory` (registered by `WeaponInstaller`), `ScreenLog`, the save system (`SaveInstaller`: `SaveService`, `SaveRegistry`, `GameSession`, `SceneLoader`) and, in dev builds, the dev console (`ConsoleInstaller`); `GameLifetimeScope` with the strict flag, installing the `SceneInstaller` components on its GameObject: `WorldTimeInstaller` (world clock), `EnvironmentInstaller` (`EnvironmentDirector` + ambience), `EnemyInstaller`, `RaidInstaller` (raid nights), `DefenseInstaller` (fences and gates) and `WorldSaveInstaller` (restore and autosave). A scene gets a system by adding its installer component. A new game's clock starts at `ClockSettings.StartHour`; a loaded one at the saved time. The MainMenu scene, the pause menu and save slots are built ([SAVE.md](SAVE.md)); a settings menu and `SettingsService` are not.

## Holding off on expensive commitments

- **Save:** built (user, 2026-11-10; [SAVE.md](SAVE.md)): versioned JSON per slot, each system its own section, no old-save compatibility promise during development (a shape change bumps `SaveService.Version`; no migrations yet).
- **Stats/modifiers:** one shared layer, `StatModifiers` (root scope, `_Common/Stats`), is every entity's `IStatProvider`: upgrades, skills and gear `Set(source, stat, add, multiply)` under their own source id and `Remove(source)`; value = (base + adds) × multiplies; saved with the game (`stats`). The player's timed buffs (`PlayerEffects`) sit on top of it. Nothing sets a modifier yet but the console (`stat.set`); `BaseStats` stays as the entity default for tests and scenes without the root scope. Enemies keep their own per-life `EnemyStats`.
- **Surfaces:** `SurfaceService` (root) names what a collider is made of from keyword rules on names and terrain layers (`Data/Surfaces/SurfaceSettings`), for footsteps and bullet impacts. No per-object tagging yet; add a rule (or later a tag component) when something is misread.
- **Interfaces:** only at real seams (Core ↔ Feature, entity ↔ outside world).

## Debug tools

## Entities: self-contained prefabs

Any entity prefab works when dropped into any scene — World, a prototype, an empty test scene.

| Kind | Examples | How it gets services |
| --- | --- | --- |
| **Unique entity** — one or a few | Player | Own `EntityScope` (a child container) |
| **Crowd entity** — many, pooled | Enemies (the goblins; `WanderCapsule` is the bare contract) | Injected once from the scene scope, no container of its own (a scope per instance doesn't scale): scene-placed ones by `EnemyInstaller`'s build callback; spawned ones only through `SpawnService`, which takes them from `PrefabPool` (created with the scene resolver, `resolver.Instantiate`, so injected before `Awake`; disabling hands them back). Flocks, items and props spawn the same way ([SPAWNING.md](SPAWNING.md)) |
| Plain object | *Not built yet* | No injection; data via `[SerializeField]` / the spawner |

```text
Unique entity root: PlayerScope : EntityScope
  ├─ own components, wired with [SerializeField]  (camera rig, CinemachineBrain, AudioListener live inside the Player)
  ├─ data: PlayerTuning (ScriptableObject → one per group)
  └─ needs from outside = small interfaces (IStatProvider…)

Parent lookup:  scene's GameLifetimeScope  →  if none: root ProjectLifetimeScope
Each need:      parent chain has it?  yes → use it   no → entity's default (BaseStats…) + one warning
```

How `EntityScope` does it (VContainer API checked in package source):

- **Parent:** overrides `FindParent()` to return the scene's `GameLifetimeScope` (or `null` → VContainer falls back to the root).
- **Defaults:** `RegisterDefault` registers a default only if `Parent.Container.TryGetRegistration(type, …)` fails (it searches the whole parent chain). A child registration would otherwise override the real service. Defaults live in the entity's system (`PlayerSystem/Defaults/`).
- **Injection:** `RegisterBuildCallback(r => r.InjectGameObject(gameObject))` injects the entity's own hierarchy. Never `RegisterComponentInHierarchy` for entity parts — it searches the whole scene and grabs another instance's component.
- **Order:** `GameLifetimeScope` gets `[DefaultExecutionOrder(-5000)]`. Without it, an entity scope whose `Awake` runs first would build against a parent with no container yet (NullReferenceException; VContainer only defers for `parentReference`, not `FindParent`). `EntityScope` itself is `-4000`, so it injects before its own components' `Awake`.
- **Strict mode:** `GameLifetimeScope.Strict` (to be on in World) turns "default used" into an error, so a missing installer in the real game can't hide behind a default. A strict scope also reports each `SceneInstaller` type it lacks, and an installer that can't install (its `Problem`) as an error instead of a warning.

**Finding each other:** `PlayerRegistry` (root scope) holds the active player as an `IPlayer`: players register themselves and it publishes `ActivePlayerChanged`. The HUD, the respawn flow, the cheats and the raids use it today. Enemies see the player through the narrower `ITargetable` (`_Common/Entities`: transform, `TargetKind`, `IsTargetable` + `IDamageable`; the player's is `IPlayerTarget`): the scene's `TargetRegistry` (EnemySystem) hands them `PlayerRegistry.Current`, plus whatever registers itself (fence segments and gates as `IBreachable`s, attacked only when the hunt has no path: [DEFENSE.md](DEFENSE.md); crops and animals later); companions will do the same. Other entities: *not built yet* (planned: an `EntityRegistry` in the root scope, which can absorb `PlayerRegistry`). No `FindObjectOfType`, no statics.

### Player

`_Core/PlayerSystem/Prefabs/Player.prefab` works dropped into any scene; scenes need no camera of their own. Hierarchy: [CODE_STRUCTURE.md → Player prefab](CODE_STRUCTURE.md#player-prefab).

- `Player` and the debug `TargetDummy` are the only gameplay MonoBehaviours with an `Update` (HUD views read the player in `LateUpdate`). Each frame it builds a `PlayerIntent` from `InputService` (or from `IPlayer.IntentSource` while a dev tool sets one: `RaidAutopilot`), then ticks plain C# parts in a fixed order: `PlayerLook` → `PlayerMotor` → `Stamina` → `Fatigue` + `PlayerBreathing` → `PlayerHeadBob` → `PlayerInteractor` → `HeldItemDriver` (equipment, the held item, zoom, sway, hands) → pose sequence → `PlayerVision`. `PlayerCameraRig` is the only writer of the camera transforms: look, head motion and pose sequences hand it their share. Tests or cutscenes can drive the motor with an intent directly.
- `PlayerMotor`: walk/sprint (`WalkSpeed` 3 m/s, sprint = walk × `SprintMultiplier` 2, forward only; speed eases with the angle between move and look: 100 % ahead, `StrafeSpeedMultiplier` 75 % at 90°, `BackwardSpeedMultiplier` 50 % at 180°; the held item's `Mobility` and aiming slow it, see WEAPONS.md; stacked slowdowns stop at `MinSpeedShare` 30 % of walking (`SlowedSpeed`), in the air too, so hops don't outrun them; sprint stamina × `HoldFeel.SprintCostScale` = 1 ÷ Mobility; `PlayerFooting` slows it by what the feet are in: water depth from the spawn system's `IWaterLevel` (lake, ponds, rivers; `WadingSpeed` curve, 1 → 0.35 from dry to 1.3 m, no sprint deeper than 0.5 m), else the ground kind found each footstep (`SurfaceSpeed`: mud and snow ×0.8), `GroundSlowdown` turns it off), crouch (Ctrl / gamepad east toggles, on stable ground only: the capsule shrinks from the top to `CrouchHeight` and the eye eases down by the difference; half walking speed; quieter footsteps; can't stand up while the standing capsule would hit something, so it stays down; jump only stands up (the next press jumps) and a fresh sprint press stands up and sprints, when there's room, and sprint held while crouching doesn't stand it back up; teleports and revives stand up), jump with coyote time and buffering, momentum kept in the air, sliding on slopes past the controller's slope limit, landing tracking (drop height, impact speed). Speeds and costs are read through `IStatProvider`.
- `Stamina`: sprint drains (walking costs nothing by default, `PlayerMovementTuning > Walk Stamina Per Second`), jump costs a chunk, shots and swings cost per weapon; every spend pauses regen, and after a delay regen runs at the full rate while the player stands idle (`PlayerMotor.IsIdle`: no move input, stable ground, nearly still) and at `PlayerVitalsTuning > Walk Regen Share` (0.5) while walking or crouch walking (`PlayerMotor.IsWalking`); none while sprinting or airborne; at 0 the player is exhausted (no sprint or jump) until it refills to a fraction. `PlayerLife` owns `Health` and fall damage (dealt through `DamageService`), linear between a safe and a lethal drop height; the player is hurt only through `DamageService` (`IDamageable` is implemented explicitly). A hit that doesn't kill raises `PlayerLife.Hurt` (`PlayerFeedback`: a rate-limited pain grunt and a short upward view flinch through `PlayerHeadBob`; the HUD's edge flash reacts to `DamageDealt`). Dying publishes `PlayerDied`. While `PlayerLife.Invulnerable` (`cheat.god`) hits apply nothing. Max health and stamina are read again when `IStatProvider.Changed` fires. `Fatigue`: under 50 / 25 / 10% stamina, eased multipliers raise gun recoil and lower melee damage, knockback and move speed; firing is never blocked ([WEAPONS.md → Fatigue](WEAPONS.md#fatigue)).
- Feel: `PlayerFeedback` plays footsteps at the bottom of each head-bob step (`PlayerHeadBob.Stepped`; the step lengthens with speed, `SlowStepLength` 0.75 m barely moving to `StepLength` 1.7 m at sprint), plus jump and landing sounds; `PlayerBreathSound` breathes heavily when out of breath (`PlayerSoundTuning`). `PlayerZoom` owns the lens: the player's `ControlSettings.FieldOfView`, narrowed by the held item's `Zoom` when aiming down sights, with look speed scaled to match; the held model keeps its own field of view.
- Equipment: keys 1–9 select hotbar slots, the mouse wheel cycles; switching holsters the held item, then raises the new one over per-item times scaled by `EquipmentConfig.SwitchSpeed`. Details: [EQUIPMENT.md](EQUIPMENT.md).
- First-person presentation: `FirstPersonRenderFeature` draws the HeldWeapon layer inside the world camera with a cleared depth and its own lens (`FirstPersonView`), so held models stay visible; the lens follows only the aim zoom (`PlayerCameraTuning.HeldAimZoomShare`), never the shot punch, sprint or sequences. It zeroes SSAO (`_AmbientOcclusionParam`) while drawing: the AO texture comes from the world's depth, so sampling it would show the scene behind through the held model. `HeldItemClearance` blends the hand back and tilts it near obstacles without moving the player; melee swings opt out.
- Pose sequences: a `PoseSequence` asset scripts a first-person moment as beats (eye height, offset, pitch / yaw / roll, field of view, ease, hold, sounds), then a settled pose with music. A `Continuous` sequence flows through its beats on one smooth path and never stops (holds only add time); a hand-held wander and a slow elliptical drift (from the last beat on) keep the frame moving, like phone footage. `Player.PlaySequence(sequence)` hands it the camera and body (no movement, no item use, the held item holstered via `Equipment.LowerHands` if the sequence asks) until `StopSequence`. Beats are placed around the feet on the ground (short of walls). Dying plays `PlayerTuning.DeathSequence` (`Data/Player/Sequences/PlayerDeath.asset`, continuous: groan on the hit, kneel and sweep the view across the grass, topple onto the side with a thud, roll onto the back and look up at the landscape with music); `EndAfter` seconds after it settles, `PlayerDeathSequenceEnded` is published (the hook for a fade / respawn). Then the root `PlayerRespawnFlow` runs the respawn in stages (`RespawnStageChanged`): Fading awaits every `PlayerRespawnFading` subscriber (the HUD's death screen closes the eyes and shows "You're dead" with "Loading..."); it takes the UI input; Preparing moves the body back to `Player.SpawnPosition` (where it entered the scene) and awaits every `PlayerRespawning` subscriber (`IAsyncPublisher`: systems that reset for a respawn finish there; `DeathTimeRule` ends a running raid and moves the clock, [RAIDS.md](RAIDS.md)); Ready waits for a click, then revives ([UI.md → Death screen](UI.md#death-screen)). It works without a HUD, and any revive (the L cheat) ends it. `Revive` stops the sequence (and its music) and publishes `PlayerRevived`. Benches, chairs and resting moments are planned as more sequences on the same player (a seat needs beats placed in an anchor's space, which was removed while unused: see git history).
- All numbers live in the `Data/Player/` tuning assets, linked from `PlayerTuning.asset` (equipment: `Data/Equipment/`; each item's numbers: its `Content/<Kind>/<Item>/<Item>.asset`).

## AI

The first AI slice was a capsule wander demo (`Content/Enemies/WanderCapsule/WanderCapsule.prefab`, kept as the bare enemy contract the Goblin builder starts from). The enemies today are animated goblins that raid the home every night from 20:00 (RaidSystem, [RAIDS.md](RAIDS.md)); none is placed in `WorldMap.unity`. Every AI agent decides with a Behavior Designer Pro tree; tasks delegate movement to `EnemyMover` (the enemy's legs over A* `FollowerEntity`). Each enemy kind has an `EnemyDefinition` in `Content/Enemies/<Name>/` (base stats, stop distance, what it targets, its behaviour tuning and sounds); the capsules use `WanderCapsule/WanderCapsule.asset`. The shared `Content/Enemies/_Shared/Wander.asset` subtree repeats a sequence: choose a reachable point, walk there, pause; its tuning is the definition's `WanderSettings` (`Data/Enemies/WanderSettings.asset`).

A scene gets enemies by adding the `EnemyInstaller` component to its `GameLifetimeScope` (navigation and `EnemySystemSettings` assigned). Enemies are found through `EnemyRegistry` (scene scope), a dense list: each `EnemyBrain` is injected once (scene-placed ones by the installer's build callback, spawned ones by the scene resolver in `EnemyPool`), starts its tree on its first `Start` and joins the registry while enabled, so spawned and pooled enemies tick like placed ones. `EnemyManager` ticks the Manual trees round-robin on a time budget: each enemy thinks about every `ThinkInterval` (1/15 s) at any frame rate, at most `MaxThinksPerFrame` trees a frame, on scaled time (paused = no thinking). `_Core/EnemySystem/Prefabs/Navigation.prefab` holds AstarPath and RVOSimulator; its default graph is a small terrain-following grid scanned on startup (for small test scenes; `Proto_*` scenes are planned). WorldMap's instance holds one tiled recast graph over the whole map, loaded at startup from a cache the map generator bakes, with lakes, ponds and rivers cut out and streams wadeable ([ENVIRONMENT.md → Navigation](ENVIRONMENT.md#navigation)). While active, an enemy also bends grass through the scene's `GrassBendField` (optional; [ENVIRONMENT.md → Stylized Grass](ENVIRONMENT.md)). Skill: `aipocalypse-enemy-ai`.

**Spawning and pooling.** Enemies spawn through the SpawnSystem like everything else ([SPAWNING.md](SPAWNING.md)). Each goblin prefab has a `Spawnable` root and `EnemyBrain` is its `ISpawnable`: on each spawn it teleports its agent (no old path survives) and appears (its appear clip, no thinking for its definition's `AppearTime` + jitter). `Die()` retires it (no longer counted as alive), and the body disabling itself after the corpse time hands it back to the `PrefabPool`. A spawnable kind has an `EnemySpawnCard` (`Content/Enemies/<Name>/<Name>_Card.asset`: prefab variants by weight, group size, placement on the navmesh, arrival cue) listed in `EnemySystemSettings.Cards` so `enemy.spawn` finds it by name. `RaidDirector` prewarms tonight's raid at scene start (each card's count, at most `AliveCap` + `CorpseHeadroom`: a dead raider keeps its instance while its body lies). Each enemy makes its kind's hit effects when it's created (`EnemyReactionSettings.EffectPrewarm`), so prewarming makes them before a fight. Who spawns what and when belongs to the caller: raids ([RAIDS.md](RAIDS.md)) and the console (`enemy.spawn <card> [count]`, `enemy.clear`, `spawn.*`). Enemies past `FarThinkDistance` (60 m) from the player think only every `FarThinkInterval` (0.25 s).

**Melee.** The goblins run the shared `Content/Enemies/_Shared/Melee.asset` subtree: a selector whose first branch hunts and whose fallback is a wander sequence. The hunt is a sequence with a `Both` conditional abort. `ChooseTarget` (re-checked every think) asks `EnemyBrain.ChooseTarget`, which picks through `TargetSelector` (best `EnemyDefinition.Targets` weight per metre; goblins: Player 1) every `RetargetInterval` (1 s), and at once when the target can't be targeted any more (dead, `cheat.notarget`), a barrier changed, or it noticed or lost the player (**Awareness** below); with no target the hunt ends and the enemy wanders. `ChaseTarget` runs at it with a `MoveSpeed` modifier: `ApproachSpeedMultiplier` (1.6) from afar, `ChaseSpeedMultiplier` (2.5) inside `EngageRadius` (5 m), where `EnemyBrain.Engaged` also puts the model in its fighting stance (`Combat` animator bool) and shouts; it repaths when the target has moved more than `max(RepathDistance, 10% of the distance)`. Inside `HoldDistance` (3.5 m) it takes one of the target's attack slots (`AttackSlots`, `EnemySystemSettings.AttackersPerTarget`: the player 3) or waits on its own spot round the target (`CrowdSpread.RingPoint` at `HoldDistance`, a new angle every `HoldShuffleTime` 4 s) facing it until one frees, so at most three goblins close in on the player at once and the rest surround instead of queueing. With a slot and within `AttackRange` (1.5 m), `MeleeAttack` stands, turns in place to face the target (`EnemyMover.Face`: a destination on itself with a facing direction, which A\* turns toward) and plays a random swing (`EnemyAnimator.Attack`) with its sounds. At `HitTime` (0.5 s) the blow lands if `MeleeHit.Lands` (the target within `HitReach` 2 m and `HitArc` 90° of the facing, on the ground plane): `EnemyBrain.Strike` → `DamageService.Deal` with the `AttackDamage` stat (`DamageType.Melee`, source the enemy) and the impact sound. Stepping out of reach before then dodges it; a swing cut short (the enemy dies, the target is gone) deals nothing. It then waits out `AttackCooldown` and swings again, or chases again when the target stepped back or the slot was lost. Hit timing comes from data, not animation events, and trees think at 15 Hz, so a blow lands within about 67 ms of `HitTime`. Tuning: the kind's `MeleeSettings` (`EnemyDefinition.Melee`; empty = the kind hunts nothing). The subtree is generated from the text spec `AgentScripts/Enemies/Melee.tree.txt` by TreeKit, so edits made in the Behavior Designer window are lost on a rebuild: change the spec.

**Animated enemies.** The goblins (`Content/Enemies/Goblin/`) are Sidekick characters in six looks (`Goblin.prefab` and five variants, picked by weight through `Goblin_Card`), each with a model and an Animator. The entity prefab nests a `Model` prefab (the vendor look, rebuilt or swapped freely); its `EnemyAnimator` writes a fixed parameter contract (`Speed` in m/s, `LookX`/`LookY`, `Lean`, `Fidget`/`FidgetIndex`) from the mover's velocity and turn rate, through the plain C# `LocomotionAnimation` rules (glances while standing, look and lean into turns, idle fidgets). `EnemyAnimationManager`, a scene `ITickable`, advances them all each frame on scaled time; no enemy has an `Update`. There is no root motion: the `FollowerEntity` moves the body and the walk clip's authored speed matches the definition's `MoveSpeed` stat. Goblins hold a sword (`Goblin_Sword.prefab`, nested on the right hand bone, no collider) closed in a right-hand grip layer, and swing it with full-body attack states. The tuning is `Data/Enemies/EnemyAnimationSettings.asset` (`EnemyDefinition.Animation`). Controllers are generated from a text spec, so any vendor's clips fit the same contract. Models cull their Animator completely off screen (safe without root motion) and draw Mesh LODs (Sidekick: up to LOD2, picked by screen size, no bias, so close goblins keep full detail); 80 goblins on screen cost ~2.3 ms main thread and ~1.6 ms GPU in the editor (numbers in the skill). Skill: `aipocalypse-characters` (vendor side: `tools-unity-synty-characters`).

**Ranged.** Two goblin kinds throw instead of closing in: the spear thrower (`Content/Enemies/GoblinSpear/`, a variant of look 02: 90 HP, 22 damage, throws from 9–14 m, up to 19 m) and the archer (`GoblinArcher/`, look 04: 70 HP, 12 damage, 16–24 m, up to 32 m). They run the shared `Ranged.asset` subtree (spec `AgentScripts/Enemies/Ranged.tree.txt`): choose a target as the melee goblins do, get to their own stand-off distance (each life picks one inside `RangedSettings.StandOff`, so a group doesn't line up), back away when the player comes inside `MinRange`, fight hand to hand with the kind's `MeleeSettings` (and their throw or draw clip: no melee clip yet) while the player is inside `MeleeRange` (2.5 m; the `TargetInMeleeReach` branch aborts both ways, so they throw again once the player is off), and throw. Their definitions give fences no weight, so they never breach: stopped by the shut fence they throw over it from wherever they are inside `MaxRange`.
- **Straight or lobbed:** `RangedAim` sphere-casts the line to the target; clear → a flat throw at `StraightSpeed`, blocked (a fence, a rock) → a lob at an angle picked at random from `LobAngle`, steeper when that arc is blocked too; one throw in seven lobs anyway (`LobAnyway`). No two arcs are the same. An archer never shoots straight through one of its own side (`RangedSettings.Friends`, the Enemy layer, within 0.5 m of the line from its chest): it lobs over them, and holds fire while no lob reaches.
- **Not always on target:** each throw leads the target by a random share of its movement (`Lead`) and goes off by a random error inside the `Spread` cone (2–2.5°); it's aimed at the moment of release, not at the start of the wind-up.
- **Readable:** a wind-up before every throw (`ReleaseTime`: 1.1 s for the spear, 0.6 s for the bow, with its sound), a bright trail on the projectile, a red ring on the ground where a lob will land, and a whistle (3D, from the projectile) once its path will pass within `FlyByRadius` of the player inside `FlyByLead` seconds. Spears and arrows stick where they land for a few seconds.
- **Flight** is `ProjectileSystem` (scene scope, one tick, plain data, pooled visuals), not a component per projectile. A projectile hurts only the kind of target it was thrown at (the player) through `DamageService` as `DamageType.Projectile`; it never hurts other enemies (its `HitLayers` leave them out) or fences.
- Content is built by `AgentScripts/Enemies/RangedGoblinSetup.cs` (after the two controllers from `GoblinSpear.animspec.txt` / `GoblinArcher.animspec.txt` and the tree). Console: `enemy.spawn goblinspear`, `enemy.spawn goblinarcher`. Not tuned or watched up close yet: the hold of the spear and the bow in the hand, the release moments against the clips, damage and accuracy numbers.

**Awareness.** An enemy hunts the player only once it knows they're there (`EnemyBrain.Alerted`, the plain `Awareness` rules): it spotted them within its kind's `EnemyDefinition.SpotRange` (goblins 20 m, spear throwers 25, archers 30; 0 = it always knows) with a clear line (`EnemySight`: one ray every 0.2 s from its eyes to the player's chest against `SightBlockers`; other enemies and barriers never block it, so a fence is seen through), it was hit by the player (`EnemyBody` → `NoticeHitFrom`, even by the killing blow; a dog's bite or a fence's thorns don't count, the dog's bite makes it Retaliate), or a neighbour that noticed shouted (`AlertRadius` 12 m, one hop: the alarmed don't pass it on). Noticing shouts (`EnemyVoice.Shout`) and re-chooses at once. `LoseSightTime` (6 s) without a sight (out of 1.5 × `SpotRange`, behind something, `cheat.notarget`) and it forgets: the player is dropped as a target. Unaware, it goes for its spawner's orders (`SpawnOrders` through `SpawnRequest.WithTag`, read from `SpawnHandle.Tag` in `OnSpawned`): raids and `enemy.spawn` send the **Farm** (`TargetRegistry.Farm`, an `ITargetable` at the middle of the fence ring that can't be hurt), so raiders break in toward it exactly as toward the player ([DEFENSE.md](DEFENSE.md)), ranged kinds wait at the fence facing it, and within `MeleeSettings.ObjectiveRadius` (10 m) of it the hunt ends and the enemy roams there (`EnemyMover.Rehome` moves its wander anchor). Camp goblins get no orders and wander as before. The alert cue is the shout and the turn; a visual cue is open. Probed in WorldMap (2026-11-11): raiders 32 m out came for the fence unaware, broke in and roamed the yard; a hit on one of three goblins 35 m away alarmed the two beside it and all three went for the fence, a fourth 25 m further stayed unaware; `cheat.notarget` made them forget after 6 s.

**Elites.** `EnemyDefinition.Elite` (`EliteSettings`, `Data/Enemies/EliteSettings.asset` for the three goblin kinds) rolls each life on the `elites` random stream (`Chance` 0.1, a flat chance until the raid's Threat decides) or is ordered by the spawner (`SpawnOrders.Elite`; `enemy.spawn goblin 3 true`): `EnemyStats` modifiers from one source (HP ×2, damage ×1.5, speed ×1.1), the body scaled ×1.15 (hit colliders with it) and the eyes swapped to the violet `EyeGlow_Elite` material (`EnemyEyes.SetMaterial`); all undone on the next activation.

**Enemy stats, damage and death.** Each `EnemyDefinition` holds base stats in an enum-keyed table (`EnemyStat`: `MaxHealth` 100 for every kind today, `MoveSpeed`, `AttackDamage`: 15 per goblin blow, 0 for the capsule); every activation builds a fresh `EnemyStats` (base + modifiers by source, `Changed` re-applies speed and max health), the seam for slows, buffs and elite tiers. `EnemyBody` (on every enemy root) is the `IDamageable` that bullets and swings reach through `DamageService.DealHit`, so hit markers, damage numbers and kill confirms work unchanged. Hits on a collider with a `Hitbox` are scaled there (`DamageService.DealHit` → `DamageInfo.OnHitbox`): every goblin's head bone carries a ×2 critical one, shown as a red number; the root capsule stops at the hips and a sphere on the upper chest covers the hunched torso, so the head isn't inside another collider. A hit pushes the body by `DamageInfo.Force` (`Knockback`: speed per N·s, exponential drag, a cap) through `EnemyMover.Push` (`FollowerEntity.Move`, which keeps it on the navmesh) and plays a directional hit reaction (light, or heavy past a push speed) on the model's upper body. A player hit that staggers an enemy, or kills it with a headshot, plays a short hit stop and camera kick (`LandedHitFeedback` on the Player prefab, `DamageResult.Staggered`), at most one every 3 s (`MinInterval`): spraying a crowd kills something every second, and back-to-back stops read as stutter. **Stagger:** each kind has a weight class (`StaggerProfile` in `Data/Enemies/Stagger/`: Light for goblins, Medium, Heavy for giants, Boss immune), linked from its `EnemyReactionSettings.Stagger`. The class scales the push (`PushScale`) and runs a meter per enemy (`StaggerMeter`): each hit adds its power (`DamageInfo.Force` magnitude, ×2 on a critical hitbox), the meter drains at `Recovery`/s, and its level picks the reaction: a twitch (the animation only), a flinch (`MoveSpeed` × `FlinchSlow` for `FlinchTime`), or a stagger (`EnemyBrain.Stagger`: halted, the swing cancelled, no thinking for `StaggerTime`, then no new stagger for `StaggerCooldown`). Goblins flinch at every rifle bullet and stagger after about five, or at one shotgun blast; a heavy kind ignores rifles and slows under rockets (a big `Force`). Weapons need nothing new: their `Knockback` is the hit power. Each hit shows the kind's blood (`EnemyReactionSettings` hit / critical / kill effects through the root `EffectPool`; `EnemyBody` is `IShowsOwnHits`, so guns and melee skip their generic impact on it). At 0 HP the colliders go off, `EnemyBrain.Die` stops the tree and the mover and turns its local avoidance off (others walk through the body), the killing hit pushes `KillPushScale` times harder, a death clip that falls away from the hit plays (even off screen), and after `CorpseTime` the visual sinks and the enemy disables itself, which hands a spawned one back to its `EnemyPool`; enabling it again revives it at full health. `EnemyBodyManager` (a scene `ITickable`) advances only bodies that are sliding or dead. Tuning: `Data/Enemies/EnemyReactionSettings.asset` (`EnemyDefinition.Reaction`). Enemies publish no enemy events: kills are `DamageDealt` with `Result.Killed`.

**Farm animals.** Cows, sheep, chickens and pigs (AnimalSystem, [ANIMALS.md](ANIMALS.md)) are the first agents that aren't enemies. They reuse the enemy legs (`FollowerEntity` + `EnemyMover`) and a Manual Behavior Designer tree (`Content/Animals/_Shared/Animal.asset`: come home at the bell or when sent, else move away from a scare, else sleep at night, else graze), but have their own bridge (`Animal`) and their own central tick (`AnimalManager`, a think every `AnimalSettings.ThinkInterval`): no `EnemyBrain`, health, targeting or spawning. What they do is decided mostly by orders, not by perception: `AnimalHerd.Orders` (the pen gate releases, the bell calls home), each animal's own `SentHome` (the player's E), and the world clock's waking hours. Their only senses: the player's position (`AnimalManager` hands it to the herd) and `ShotFired`, the gunshot event `HeldGun` publishes. Enemies don't target them yet.

**Service robots.** The home robots (RobotSystem, [ROBOTS.md](ROBOTS.md)) follow the animals' pattern: the enemy legs and a Manual tree (`Content/Robots/_Shared/Robot.asset`: flinch, step aside, answer the whistle, greet, nervous, standby at night, idle and stroll), their own bridge (`Robot`) and central tick (`RobotManager`, which also turns their heads in `LateTick`). They react to the player (looks, E, hold E, the whistle through `IWhistleTarget`, bumps, a pointed gun, hits that apply nothing) and to raids and the player coming home, and are never targets. Their request and reaction timers are plain C# (`RobotState`); what a robot does is its `RobotRole` (a `RobotService` asks for a menu with `RobotServiceRequested`, a `RobotJob` supplies work for the tree's Work branch); how it moves is an `IRobotLegs` (ground legs over `EnemyMover`; a flyer brings its own). Robots alone walk ground tagged `NavTags.RobotsOnly` (the house and its door link): every other `EnemyMover` leaves it out. The door hop sits in its own asmdef, `MB13.Aipocalypse.RobotLinks`, because A*'s link handler needs Unity.Entities, which Core doesn't reference.

**Enemy sounds.** A kind's `EnemySoundSet` (`EnemyDefinition.Sounds`; goblins: `Goblin_Sounds.asset`, entities in the `Enemies` BroAudio library) is played at the enemy through `AudioService.PlayAt` by its `EnemyVoice` (plain C#, one per brain) from the existing hooks: `MeleeAttack` (swing, plus the attack voice on some swings), `EnemyBrain.Strike` (impact), `EnemyBody` (hurt, rate-limited so a shotgun volley gives one cry; death), `Engaged` (shout, with a per-enemy cooldown). Footsteps come from `EnemySoundManager`, a scene `ITickable`: a step per stride for each enemy within its kind's `FootstepRange` (20 m) of the player, at most `MaxFootstepsPerSecond` (12) all together. No enemy has an `AudioSource` or an `Update`; BroAudio playback groups cap how many goblin voices and steps play at once. Unset sounds stay silent.

## Performance

Standards that apply to all gameplay code now:

- **Zero allocations per frame:** no LINQ, no `new` in hot paths, no boxing, no string building in `Update`. Event payloads are structs.
- **DI is setup-time only:** resolve and inject at creation, never per frame.
- **One update per entity, explicit order:** a view ticks its plain C# parts (as `Player` does) instead of each part having its own `Update`. Many-instance things get one central tick (VContainer `ITickable`), not an `Update()` each.
- **Pool everything that spawns repeatedly** (`UnityEngine.Pool`) and prewarm pools before they're needed.
- Measure before optimising (Profiler, `ProfilerMarker`s); don't assume.

Per-system budgets (enemy counts, stress scenes) get added here with those systems.

- **Enemies** (no budget measured yet): `PrefabPool` prewarms before enemies are needed (2 a frame, each woken once off-stage so `Awake` and `Start` are paid while loading; `RaidDirector` prewarms tonight's raid at scene start, `AliveCap` + `CorpseHeadroom`, so no raider is instantiated mid-fight; blood effects are made with each enemy). `SpawnService` wakes queued group members within `SpawnBudgetMs` (2 ms) a frame: a prewarmed goblin wakes in about 1.1 ms (editor; a never-woken one cost about 3.4 ms with its next-frame `Start`, six in one frame made a 22 ms frame). Spawned instances live at the scene root (a shared parent serialised animation write-back: 0.50 vs 0.36 ms for 30 goblins). A raid keeps at most `AliveCap` (12) raiders alive, trees think on the `EnemyManager` budget (far ones every 0.25 s), and footsteps come from one central tick capped per second (`EnemySoundManager`). Raid soak after the SpawnSystem (2026-11-02, editor): night cleared, 18/18 spawned, game time avg 11.1 ms, p95 14.1 ms, no errors. 300 wandering goblins through `SpawnService` (`AgentScripts/Spawning/SpawnPlayCheck.cs` → `Crowd`, editor): arrival 5.1 s (spawn path p95 2.8 ms a frame), steady PlayerLoop median 13.7 ms (15.1 with every enemy thinking at full rate), trees 0.18 ms. The ROADMAP gate wants this measured in a build. Wake breakdown: [SPAWNING.md → Reference](SPAWNING.md#reference).
- **Night fight** (`PerfSuite.Fight`: 25 goblins on the raid approach at 22:00, AK fire at the nearest, kept topped up; editor, RTX 5070 Ti laptop, 2026-11-01): warm PlayerLoop median 10–12 ms, p99 12–18 ms, of which about 3.5 ms is the profiler's own memory-counter flush; a bullet hit costs ≤ 0.7 ms (`Aipocalypse.DamageService.Deal`, kill and blood included), waking a pooled goblin about 2 ms (`Aipocalypse.EnemySpawner.Spawn`) plus 1.5 ms for its first `Start`. A fresh play session adds one-off 5–9 ms frames on the first shot, first hit, first headshot-kill feedback and first bullet-hole decals: mostly editor JIT (Standalone builds are IL2CPP), so judge them in a build. Markers on the hit path: `Aipocalypse.BulletSystem.Advance`, `Aipocalypse.DamageService.Deal` / `.Publish`, `Aipocalypse.EnemySpawner.Spawn`, `Aipocalypse.EnemyPool.Prewarm`.

## Prototypes → main game

Mechanics are built and tested in small scenes under `Assets/_Game/Scenes/Prototypes/` (not in Build Settings). Today the mechanics are tested together in `Assets/_Game/Scenes/Prototypes/WorldMap.unity`; guns and their parts also in `WeaponsTest.unity` (no scope of its own: the Player and HUD prefabs on root services).

1. **Only the scene is a prototype, never the code.** Mechanic code goes in its real folder (Core, Feature or Experimental) from day one. No `Proto*` copies of classes or prefabs.
2. **A prototype scene needs no scope of its own.** Drop in the entity prefabs (and `HUD.prefab` if you want the HUD); they run on root services + their defaults.
3. **Real systems via installers.** When a prototype needs a real system, add a `GameLifetimeScope` with just those `SceneInstaller` components. World uses the same class with all of them, strict.
4. **Defaults belong to the entity's system** (e.g. `PlayerSystem/Defaults/BaseStats`) — they are part of the entity's contract.
5. **Tuning lives in ScriptableObjects** under `Assets/_Game/Data/`, shared by every scene.
6. **Each mechanic can be turned off on its own.** Its own installer or component, an `Enabled` flag (or similar) in its settings asset when that's cheap, and links to other systems only through MessagePipe events or optional services (`TryResolve`), so switching it off, swapping or removing it touches nothing else (AGENTS.md → Scope of a change).
7. **Smoke test** (PlayMode): `Tests/PlayMode/WorldMapSmokeTests.cs` loads `WorldMap.unity`, checks injection and the enemy system, picks up a gun, fires and reloads, and jumps the clock to the raid's start hour to check raiders spawn; any logged error fails it.

A prototype is done when it works in its scene **and** in World with no code changes.

```text
  Data/                   settings shared by a whole system, one folder per system (one copy each: PlayerTuning, EquipmentConfig,
                          AmmoConfig, ClockSettings, EnemySystemSettings, RaidSettings + raid plans, UI styles, Audio libraries, HandSet + poses,
                          Environment/TimeOfDay)
  Scenes/Prototypes/      WorldMap.unity (data in Maps/WorldMap/), WeaponsTest.unity, Proto_* scenes (scene-only assets in a folder named after the scene)
  Settings/               URP assets, Input System actions
  _Editor/                editor-only tools that aren't game code (player builds, BUILD.md). asmdef MB13.Aipocalypse.Editor
  Tests/EditMode/  Tests/PlayMode/
```

- **Content or Data?** It belongs to one weapon, item, enemy or animal → `Content/<Kind>/<Name>/`. One copy shared by the whole system → `Data/<System>/`. Used by several things of one kind → `Content/<Kind>/_Shared/`.
- **Map or Environment?** Only one map uses it (its terrain, heightmaps, water meshes) → `Maps/<Map>/`. Another map could use it (a water material, a terrain layer, a vegetation copy) → `Environment/`.
- **Names** keep the thing's name (`AK47_Repair`, not `Repair`): the object picker shows only file names. Map assets get no map prefix (the folder says which map); first-party copies of vendor assets keep the source pack's prefix (`BK_`, `HL_`, `KN_`, `AM_`, `GL_`).
- **Making a prototype map official:** rename its `Maps/<Map>/` folder and scene, update its generator's path constants, and add the scene to Build Settings.
