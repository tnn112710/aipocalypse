# Code structure

Map of the scripts that exist today: where each one lives, what it owns, and how they connect. The *why* (layers, scopes, Core vs Features) is in [ARCHITECTURE.md](ARCHITECTURE.md). **Update this file whenever you add, move or remove a script.**

## Assemblies and namespaces

| Assembly | Folder | References |
| --- | --- | --- |
| `MB13.Aipocalypse.Core` | `Assets/_Game/_Core/` | VContainer, MessagePipe (+ .VContainer), UniTask, Unity.InputSystem, Unity.Cinemachine, UnityEngine.UI, Unity.TextMeshPro, AstarPathfindingProject, PackageTools, Drawing, Unity.Animation.Rigging, DOTween.Modules, MoreMountains.Tools, BroAudio, DamageNumbersPro, Unity.RenderPipelines.Core.Runtime, Unity.RenderPipelines.Universal.Runtime, sc.stylizedgrass.runtime, CodeStage.AFPSCounter.Runtime, EasySave3 (Easy Save 3 with its assembly definitions enabled), Unity.Localization, Unity.ResourceManager; precompiled plugin DLLs auto-referenced |
| `MB13.Aipocalypse.Tests.EditMode` | `Assets/_Game/Tests/EditMode/` | `MB13.Aipocalypse.Core`, `MB13.Aipocalypse.Editor`, VContainer, MessagePipe (+ .VContainer), UniTask, BroAudio, Unity.Localization (+ .Editor), Unity.ResourceManager, Unity.TextMeshPro, UnityEngine.TestRunner, UnityEditor.TestRunner; precompiled (overrideReferences) `nunit.framework.dll`, `DOTween.dll`. Editor only |
| `MB13.Aipocalypse.Tests.PlayMode` | `Assets/_Game/Tests/PlayMode/` | `MB13.Aipocalypse.Core`, VContainer, test runner, NUnit |
| `MB13.Aipocalypse.Editor` | `Assets/_Game/_Editor/` | `MB13.Aipocalypse.Core`, Unity.Localization (+ .Editor), Unity.Addressables (+ .Editor), Unity.ResourceManager, Unity.TextMeshPro (Odin attributes auto-referenced). Editor only: tools that aren't game code (player builds) |

Namespaces follow the folder: `MB13.Aipocalypse.Core.<Folder>` (e.g. `MB13.Aipocalypse.Core.PlayerSystem`, `MB13.Aipocalypse.Core.Combat`). One exception: input uses **`MB13.Aipocalypse.Input`**, because a namespace ending in `InputSystem` shadows `UnityEngine.InputSystem.InputSystem`.

- Only `Player` gets injected. The parts are plain classes it creates and owns. They get Unity components through their constructors, not through DI.
- Outside systems see the player through `PlayerRegistry.Current`, an `IPlayer` (HUD, respawn flow, cheats, raids). Enemies hunt `ITargetable`s (`_Common/Entities`: transform, `TargetKind`, `IsTargetable` + `IDamageable`): `TargetRegistry` hands them the active player (once they've noticed them), the Farm (the middle of the fence ring) for raiders that haven't, and the barriers in the way; their blows go through `DamageService.Deal`.
- `RaidSystem` → `EnemySystem` (enemy cards), `SpawnSystem` (groups through `SpawnService`, zones), `WorldTimeSystem` (`WorldClock`) and `PlayerSystem` (`PlayerRegistry`; `PlayerRespawning` from its respawn flow); `EnemySystem` never knows about raids. `DeathTimeRule` ends a raid and moves the clock behind the death screen.
- Dev tools may play the player through `IPlayer.IntentSource` (`RaidAutopilot`), which replaces only the `InputService` read; nothing else reads devices.
- `PlayerSystem` → `EquipmentSystem` ← `WeaponSystem`: the player owns an `Equipment`; weapon kinds derive from equipment's definitions. `EquipmentSystem` knows neither the player nor weapons: `WorldItem` finds the picker's inventory through `IEquipmentOwner`, a `LootContainer` hands itself to the searcher through `ILooter`, and a `HeldGun` finds its holder's ammo and aim through `IGunUser`, a `HeldMelee` its eye and root through `IWeaponUser` (Player implements all of them). The player also uses a few `WeaponSystem` types directly (`AmmoReserve`, `AimOrigin` in its tuning).
- `EnemySystem` → `EnvironmentSystem`: `EnemyBrain` `TryResolve`s the scene's `GrassBendField` and joins it while active. No field = no bending.
- `AnimalSystem` → `EnemySystem` (`EnemyMover` as the animals' legs, the scene's `AstarPath`), `WorldTimeSystem` (`WorldClock`), `PlayerSystem` (`PlayerRegistry`), `EquipmentSystem` (Tokens as `WorldItem` pickups) and `EnvironmentSystem` (`GrassBendField`); it hears gunshots through `ShotFired` (`_Common/Events`, published by `WeaponSystem`'s `HeldGun`). Nothing depends on it: remove its installer and the animals just stand there.
- Enemies and weapons share the root `EffectPool` (`_Common/Effects`): `EnemyBody` spawns its kind's blood (`PooledEffect`s in `EnemyReactionSettings`, made with each enemy, `EnemyBrain.Construct`). Guns and melee know nothing of enemies: they skip their generic impact on any `IShowsOwnHits` (`_Common/Combat`).
- `PlayerSystem` → `EnvironmentSystem`: the player's `VisionLight` carries a `TimeOfDayWeight` (Darkness) that the scene's director ticks; `Player` only reads its `Weight`. No director (prototype scenes) = never dark, light off.
- Bullets, swings and falls hurt anything with an `IDamageable` (`_Common/Combat`) through `DamageService.Deal`, which applies `TakeDamage` and publishes `DamageDealt` (source, result). Targets only apply their own rules.
- Interaction: `_Common/Interaction.IInteractable` is the only contract (plus the optional `IHoldInteractable` second use and the `ICollectInteractable` use on the Collect key). `PlayerInteractor` finds one with a look cast; the interactable decides what happens (`WorldItem` → `Equipment.TryPickUp`, `LootContainer` → `ILooter.BeginLoot` → `PlayerLooting`, `BarrierSegment` → open / close a gate, or Repair All when the actor's `IRepairer` holds a tool). A held tool's own key is the player's: `PlayerRepair` asks the focus for its `IRepairable.TryGetRepairPrompt` and knocks on R.
- Ghosts: anything can be an `_Common/Ghosts.IGhostSource`; whoever shows it asks every frame and draws it with `GhostDrawer.Draw` and its own `GhostStyle`. The player shows its repair target's ghost, else its interact focus's. A placement tool later captures a `GhostShape` from the prefab it places (`GhostShape.Capture(prefab.transform)`), draws it at the aimed pose and picks Valid / Invalid itself. A highlight over something in place uses `GhostShape.CaptureLive` and its own material and tint (`RepairHighlight`).
- QTEs: `QuickTimeSystem` knows no weapons. A gun's `GunRepairFlow` starts a session; the HUD's `QteHud` shows any session from the QTE events, and `_Common` events carry no weapon types.
- Inside the player system, plain C# events are used (`PlayerMotor.Landed`, `PlayerLife.Died`). Anything crossing systems goes through MessagePipe (`DamageDealt`, `PlayerDied`).

## Adding a script

- **New system:** folder under `_Core/` (or `Features/` / `_Experimental/`), namespace `MB13.Aipocalypse.Core.<System>`, one installer. A root service installs from `ProjectLifetimeScope` (`<System>Installer : IInstaller`); a scene system is a `SceneInstaller` component added to the scene's `GameLifetimeScope` GameObject. Add it to the map above.
- **Rules go in plain C#** (testable, EditMode tests in `Tests/EditMode/`). MonoBehaviours are views: they wire components and forward to the rules.
- **Numbers go in a ScriptableObject** type next to the system, with the asset in `Data/<System>/`.
- **Console commands and cheats:** `<System>Commands.cs` next to the system's installer, registered there when `Cheats.Enabled` ([CONSOLE.md → Adding a command](CONSOLE.md#adding-a-command)).
- **New `*LifetimeScope.cs`:** `DisableScriptModifier` is on, but check that VContainer didn't replace the file with its template.
- **Generated code** (`GameInputActions.cs`): change the `.inputactions` asset, never the file.
